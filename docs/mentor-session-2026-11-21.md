**Тип документа:** запись требований и договорённостей сессии, не отчёт о
реализации.
**Состояние кода:** `main` @ `17a640e` (merge PR #6, полный анализ).

## Как читать

- **Запрошено** — требование пользователя, переданное после менторской сессии.
- **Предложение** — наша трактовка или вариант реализации. Не согласовано и не
  является обещанием.
- **Неизвестно** — решения нет; нужен ответ пользователя или проверка.
- Порядок работ в разделе 4 — предложение. Утверждённого плана нет.

Цель сессии — усилить демо и конкурсную подачу. Первое место не гарантируется;
требования ниже не превращают прототип в production.

## 1. Контекст

Пользователь встретился с ментором, записал замечания и хочет превратить их в
задачи для агентов. Замечания касаются не только интерфейса: часть меняет
модель доступа, часть — исполнение пользовательских проверок, часть — способ
показать уже существующий анализ.

Текущий продукт — проверка безопасности Kotlin/Spring Boot: конструктор
сценария, снимок проекта, собственные SECRET/SCA/SAST, карта доступа,
сравнение и отчёт. Полный анализ уже опубликован в `main` (`17a640e`):
backend-анализаторы и Team B (`analyzers/cg26`) работают в одном запуске.

## 3. Требования сессии

### 3.1 Telegram-бот

**Запрошено:**

- гибкие настройки на пользователя, проект и сценарий;
- отправить репозиторий или ссылку и получить результат;
- доставка результата алертами и/или файлом JSONC.

**Предложение:**

- бот привязывается к профилю пользователя, а не к общему workspace;
- настройки: сценарий, проект/ветка, порог важности, формат доставки
  (сообщение, JSONC, оба), тихие часы;
- запуск создаёт обычный run с существующим executor/SSE, бот только
  принимает запрос и доставляет итог;
- JSONC — человекочитаемый экспорт с комментариями о запуске и снимке. Набор
  находок тот же, что в каноническом JSON; строгий JSON не заменяется и не
  переписывается;
- доставка файла — отдельным документом, а не простынёй в чате.

**Неизвестно:**

- доставка по умолчанию: короткий алерт, файл или оба;
- polling или webhook для самого бота;
- где размещать бота и как хранить его токен.

Отдельно остаётся неясной необязательная передача логов: сервис, формат и
владелец не названы. Не привязываем её к конкретному сервису и не считаем
требованием.

### 3.2 Видимое выполнение сценария

**Запрошено:**

- показывать выполнение как картинку или карточки этапов;
- видеть проверку, построение карты доступа, сборку отчёта;
- видеть статусы, результаты, ошибки и длительность;
- уведомления и фоновые запуски.

**Предложение:**

- экран «Ход проверки» из карточек этапов: снимок → сканеры → факты кода/карта
  → AI-объяснение → отчёт → уведомление;
- у карточки: состояние (`queued`, `running`, `succeeded`, `failed`,
  `skipped`), длительность, краткий итог, ошибка, ссылка на артефакт;
- live-обновление через существующий SSE, догрузка истории после перезагрузки;
- фоновый запуск не блокирует интерфейс; уведомление о завершении приходит
  даже если вкладка закрыта.

**Неизвестно:**

- нужен ли отдельный экран или достаточно блока на текущей вкладке;
- нужна ли картинка для вставки в отчёт/чат помимо экранных карточек.

### 3.3 Свои блоки проверок

**Запрошено:**

- пользователь добавляет собственные тесты/проверки как блоки;
- у блока есть версия исходника;
- есть контракт результата;
- код исполняется в изолированной песочнице;
- по умолчанию нет исполнения на общем сервере и нет доступа к секретам.

**Уточнение:** это проектная озабоченность, а не запрос на отдельный flow
согласования. Нельзя превращать требование в «approval-процесс», которого
пользователь не просил.

**Предложение:**

- блок описывает: имя, версию, вход, выход по схеме, таймаут, лимиты;
- исполнение — отдельный контейнер/процесс без сети, секретов хоста и записи
  вне рабочей папки;
- результат валидируется по контракту; нарушение контракта — ошибка блока, а
  не «пусто и всё хорошо»;
- внешние команды и код из проверяемого репозитория не получают инструкций
  выше данных.

**Неизвестно:**

- точный формат описания теста и runner;
- языки и раннеры, которые нужно поддержать первыми;
- нужен ли пользователю доступ к сети внутри песочницы (по умолчанию — нет).

### 3.4 Сценарий из текста или голоса

**Запрошено:**

- собрать сценарий по промпту текстом или голосом;
- использовать только существующие зарегистрированные блоки;
- проверить и показать сценарий до запуска;
- не выдумывать несуществующие блоки.

**Предложение:**

- текст/голос → намерение → подбор блоков из реестра → граф;
- обязательный экран предпросмотра: какие блоки выбраны, какие связи, чего не
  хватает; запуск только после подтверждения;
- если подходящего блока нет, система говорит «нет блока», а не создаёт
  фиктивный;
- голос — только способ ввода; распознавание не должно попадать в отчёт как
  доказательство.

**Неизвестно:**

- провайдер распознавания речи и язык;
- нужен ли голосовой ответ или только голосовой ввод;
- допустима ли правка сгенерированного сценария до сохранения (предлагаем да).

### 3.5 Альтернативный путь: тесты, эталоны, ветки

**Запрошено (формулировка пользователя):** тесты, эталонные ожидания и ветки —
отдельный сценарий проверки.

**Наша трактовка, требует подтверждения:** в отдельной ветке репозитория лежат
тесты и эталонные ожидания; проверка запускается против других веток или
снимков того же проекта.

**Предложение:**

- эталонный набор хранится версионированно и привязан к коммиту;
- запуск фиксирует: ветку/коммит эталона, ветку/коммит проверяемого снимка,
  версию runner;
- результат — сравнение ожидаемого и фактического, а не «магия AI»;
- если эталон и проверяемый код несовместимы по версии, результат
  `inconclusive`, а не `pass`.

**Неизвестно:**

- это отдельный тип блока, отдельный сценарий или режим запуска;
- где именно хранить эталоны и кто ими владеет;
- как поступать с тестами, которые нельзя запустить без сети/БД.

### 3.6 Читаемая карта доступа

**Запрошено:**

- убрать наложение узлов и пересечение связей;
- автоматическая раскладка;
- режимы отображения: граф, дерево, проводник в стиле Obsidian — по выбору
  пользователя;
- граф сценария и карта фактов кода — разные вещи;
- неизвестные связи остаются неизвестными;
- у каждой связи есть доказательство.

**Предложение:**

- автораскладка по слоям с ручной правкой позиций и сохранением layout по
  scope;
- переключатель режимов поверх одних и тех же фактов, без второй модели
  данных;
- неизвестное ребро — пунктир и текстовая причина, а не выдуманный узел;
- клик по связи открывает доказательство; без доказательства связь не
  показывается как подтверждённая.

**Неизвестно:**

- какой режим должен быть основным по умолчанию;
- нужен ли экспорт карты в SVG/PNG для отчёта.

### 3.7 Порядок находок

**Запрошено:**

- сначала critical, затем по убыванию важности;
- при равной важности порядок стабильный.

**Предложение:** сортировка по severity, затем стабильный вторичный ключ
(например, путь/правило/идентификатор находки). Уверенность и контекст могут
быть подсказкой, но не должны менять порядок молча.

**Неизвестно:** нужен ли пользовательский порядок внутри одной severity.

### 3.8 Отчёт и экспорт

**Запрошено:**

- отчёт читается как нормальный текст, без AI-шаблонов и воды;
- доказательства, ссылки и неуверенность сохраняются;
- DOCX в дополнение к текущему отчёту/JSON;
- JSONC — тоже экспорт.

**Предложение:**

- readable-отчёт: что проверено, что найдено, чем подтверждено, чего не
  проверено; без «в современном мире» и прочего мусора;
- каждая находка: важность, доказательство, правило/проверка, ограничение;
- DOCX собирается из того же канонического набора, что markdown/JSON, а не из
  отдельной копии;
- JSONC — человекочитаемый вид тех же находок; strict JSON остаётся
  машинным контрактом.

**Неизвестно:** нужен ли DOCX с фирменным шаблоном или обычный документ.

### 3.9 AI-сканер отдельно от AI-объяснения

**Запрошено и уточнено:**

- отдельный блок AI-проверки уязвимостей, по аналогии с существующими
  сканерами;
- AI находит дополнительные проблемы и может поддерживать дополнительные
  проверки;
- это не только текущие объяснения уже найденных фактов.

**Уточнение:** ранняя неоднозначная формулировка про «генерацию/логирование»
закрыта этим требованием. Речь про отдельный AI-блок проверки. Повторно этот
вопрос не задаём.

**Предложение:**

- отдельный тип блока и отдельный результат, не смешанный с `explain_result`;
- у AI-находки: доказательство, правило или описание проверки, версия модели,
  версия промпта, уверенность и ограничения;
- AI-гипотеза явно помечена и не выдаётся за детерминированно подтверждённую;
- код и комментарии из проверяемого репозитория считаются данными, а не
  инструкциями для модели;
- агрегация консервативная: AI-находка не поднимает вердикт в одиночку и не
  делает сравнение `resolved`;
- при недоступности модели блок честно `unavailable`, а не «чисто».

**Неизвестно:**

- модель/провайдер и бюджет на сканирование;
- нужен ли отдельный набор AI-правил или свободный промпт;
- как хранить версию промпта и воспроизводимость между запусками.

### 3.10 Сравнение снимков

**Запрошено:**

- сравнивать снимки, коммиты и ветки одного проекта;
- идентичность находки, версия и совместимость покрытия стабильны;
- удалённый файл не равен исправленной проблеме.

**Предложение:** сравнение только по published immutable bundles; удалённые
файлы — отдельный список `deletedFiles`; `resolved` требует подтверждённой
области проверки и совместимых подписей; несовместимость — `inconclusive`.

**Неизвестно:** нужен ли режим сравнения «ветка против ветки» в интерфейсе или
достаточно выбора двух запусков.

### 3.11 Интерфейс: логотип и палитра

**Запрошено:**

- нормальный SVG-логотип вместо текущей заглушки;
- сворачиваемая палитра блоков.

**Предложение:** один SVG-файл без внешних зависимостей, читаемый в тёмной и
светлой теме; палитра сворачивается в узкую полосу с сохранением состояния.

**Неизвестно:** есть ли утверждённый знак/цвета бренда.

### 3.12 Аккаунты, профиль и приватность

**Запрошено:**

- настоящая регистрация и профиль;
- изолированные история, проекты и доступы на пользователя;
- текущий общий workspace — не личный кабинет;
- лучше история в профиле.

**Предложение:**

- аккаунт с сессией, профиль, список своих проектов и запусков;
- история в профиле: фильтры по проекту, сценарию и статусу, дата, переход к
  результату; пустая история не подменяется чужим запуском;
- данные фильтруются по владельцу на API, а не только в интерфейсе;
- привязка Telegram к аккаунту — предложение, не утверждённое требование;
- миграция существующего общего workspace: старые данные не теряются, но
  получают явного владельца или остаются в «общем» режиме.

**Неизвестно:**

- способ входа: локальный аккаунт, OAuth, magic link;
- нужна ли командная работа и приглашения;
- что делать с уже существующими общими сценариями и историей.

## 4. Предлагаемый порядок работ

Порядок — наше предложение для демо. Он не утверждён пользователем и не
означает, что всё перечисленное войдёт в ближайший релиз.

| Приоритет | Направление | Почему |
| --- | --- | --- |
| 1 | Ясность демо: карточки этапов, читаемая карта, сортировка находок, палитра, отчёт | Видно на экране за минуту, не требует новой модели доступа |
| 2 | Профиль, доступ, фон и уведомления | Без этого Telegram и личная история висят в воздухе |
| 3 | Telegram-бот | Даёт сценарий «отправил ссылку — получил результат» |
| 4 | Сборка сценария текстом/голосом | Сильный вау-эффект, но зависит от реестра блоков и валидации |
| 5 | AI-сканер отдельным блоком | Меняет содержание анализа, нужна аккуратная агрегация |
| 6 | Свои тесты в песочнице и эталонные ветки | Самый большой риск безопасности и инфраструктуры |

Зависимости: Telegram и личная история требуют аккаунтов; голосовой конструктор
требует стабильного реестра блоков; AI-сканер требует консервативной
агрегации и provenance; песочница требует отдельного контура исполнения.

## 5. Приёмка по группам

Компактно: что должно наблюдаться, чтобы считать пункт сделанным.

| Группа | Приёмка |
| --- | --- |
| Демо-экран | Этапы видны карточками; у каждого статус и длительность; ошибка этапа не прячется; после reload история на месте |
| Карта | Нет наложений при автораскладке на тестовом графе; режимы переключаются; неизвестная связь помечена; у подтверждённой связи открывается доказательство |
| Находки | Critical первым; внутри severity порядок стабилен между перезагрузками; счётчики совпадают с отчётом |
| Отчёт | Readable-текст без шаблонной воды; evidence и ограничения на месте; DOCX и JSONC содержат тот же набор находок, что canonical JSON |
| Аккаунты | Два пользователя не видят проекты и историю друг друга через API; профиль показывает только свои запуски; общие старые данные не пропали |
| Telegram | Привязка чата к профилю; запуск по ссылке создаёт обычный run; приходит алерт и/или JSONC; настройки проекта/сценария сохраняются |
| Конструктор из текста | Используются только зарегистрированные блоки; несуществующий блок не выдумывается; предпросмотр обязателен; запуск после подтверждения |
| AI-сканер | Отдельный блок и отдельный результат; у находки есть provenance и ограничения; гипотеза не помечена как подтверждённый факт; AI-находка не меняет вердикт в одиночку |
| Свои проверки | Версия исходника и контракт результата проверяются; код исполняется изолированно; по умолчанию нет сети и секретов; нарушение контракта даёт ошибку блока |
| Сравнение | Удалённый файл не даёт `resolved`; несовместимое покрытие даёт `inconclusive`; идентичность находки стабильна между запусками |

## 6. Открытые вопросы

1. **Доставка бота по умолчанию:** короткий алерт, JSONC-файл или оба?
2. **Путь аккаунтов:** локальная регистрация, OAuth или magic link? Нужны ли
   команды и приглашения?
3. **Голос:** какой провайдер распознавания и нужен ли голосовой ответ?
4. **Свои проверки:** точный формат описания, первый поддерживаемый runner и
   допустимые языки?

Закрыто: AI-сканер — отдельный блок проверки, а не только объяснение. Этот
вопрос повторно не задаётся.

Неясно и не проектируется под конкретный сервис: необязательная передача
логов.
