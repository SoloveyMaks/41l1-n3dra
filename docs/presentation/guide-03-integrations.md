# GitHub и GitLab: импорт, наблюдение и push-событие

## Импорт — это снимок коммита, а не рабочая копия

В NEDRA проект можно добавить ZIP-архивом или корневой ссылкой на публичный репозиторий GitHub/GitLab. Для ссылки сервер сначала проверяет форму URL: только `https`, только `github.com` или `gitlab.com`, без логина, пароля, порта, query, fragment и процентов в пути. Затем он определяет ветку — указанную или ветку по умолчанию — и получает её текущий commit SHA. Архив скачивается уже по этому SHA, поэтому движение ветки после resolve не меняет содержимое проверки. ZIP проходит тот же безопасный intake: лимиты размера, числа файлов и путей, symlink и compression ratio; provider-корень снимается, `.git` и `node_modules` не попадают в анализ. Submodules и Git LFS не скачиваются, поэтому вместо них остаются указатели; это снимок для анализа, а не рабочая копия.

Пример: ссылка `https://gitlab.com/group/sub/repo.git/` канонизируется в `https://gitlab.com/group/sub/repo`, импорт фиксирует полный SHA и создаёт неизменяемый артефакт. Повторный импорт после нового коммита — это новый артефакт и новый SHA; старые проверки не перезаписываются. Приватные репозитории, токены и произвольный коммит не поддерживаются.

## Наблюдение: опрос и push

Наблюдение создаёт подтверждённый аккаунт workspace; в API это `require_workspace_actor`, в UI — админ-панель. Для режима опроса задаётся `interval:` не чаще 60 секунд (по умолчанию 300) или cron; при создании запоминается текущий коммит ветки, поэтому скрытого первого анализа нет: сначала проект импортируют и проверяют вручную, а watch реагирует только на новые коммиты. «Пауза» выключает и опрос, и push; «проверить сейчас» — явная разовая проверка. Durable ledger `(watch, SHA)` не даёт двум процессам импортировать один коммит и создать два run; состояния `processing/queued/running/done/failed` переживают рестарт, а курсор `last_seen_commit` означает «поставлено в очередь», не «анализ успешно завершён».

## Путь push-события

Для push-режима создаётся отдельный адрес `/api/repository-hooks/<watch_id>`. Секрет выводится HMAC-ом из серверного ключа, workspace, watch и nonce; plaintext в БД не пишется, старый секрет после ротации получает 401. Провайдер подписывает тело: GitHub — `X-Hub-Signature-256`, GitLab — `X-Gitlab-Token`; сравнение идёт по байтам и до разбора JSON. Событие проверяется на тот же репозиторий, ветку и отсутствие удаления, затем durable-запись в inbox и ответ 202 — без ожидания скачивания. Повтор доставки отсекается по delivery id/дайджесту; обработчик импортирует точный SHA и ставит один run. Пример: push в `refs/heads/main` с SHA `abc…` создаёт 202, затем run; push в тег или другую ветку — `ignored`, без запуска.

Для пользователя это означает: проверка привязана к конкретному коммиту, а не к «последнему состоянию». Для защиты: «импорт и watch разделяют snapshot, ledger идемпотентности, а push аутентифицируется секретом до создания побочных эффектов». Внешний хук нужно установить вручную; реальная доставка GitHub/GitLab в этой приёмке не проверялась, синтетические подписанные события не выдаются за неё.

# Расписание и повторяемый процесс

## Что именно запускается

Расписание — это сохранённая привязка «сценарий + артефакт + cadence», а не фоновый поток с бесконечным `sleep`. Пользователь workspace с подтверждённой сессией создаёт запись через API расписаний; сервер проверяет, что сценарий и артефакт существуют, и сохраняет `cronOrInterval` и `enabled`. В момент срабатывания scheduler берёт не текущий черновик, а сохранённую ревизию сценария и зафиксированный артефакт; run получает `trigger_type=schedule`. Поэтому расписание воспроизводимо: оно не «додумывает» новый проект и не смешивает изменения, сделанные после настройки. Время cron/interval считается в UTC; колонка `timezone` в таблице есть, но текущий путь планировщика использует UTC, и это важно проговорить, если пользователь ждёт локальное время.

Пример: `interval:300` означает «не чаще чем раз в 300 секунд»; cron `0 * * * *` — начало каждого часа по UTC. Если сценарий или артефакт удалены, слот не превращается в скрытый успех: run не создаётся, расписание сдвигается; это ограничение наблюдаемости, а не успешный анализ.

## Аренда слота, пересечения и границы

Scheduler просыпается каждые 5 секунд, забирает пачку due-расписаний (до 20) и ставит на строку lease на 60 секунд. Внутри процесса не больше четырёх активных schedule-run; для одной пары workspace+schedule одновременно допускается только один активный запуск. Если слот наступил, пока предыдущий run ещё идёт, система не запускает второй параллельно и не копит «догоняющие» запуски: она освобождает lease и переносит следующее срабатывание. Это политика переполнения, а не потеря: пользователь видит последний запуск и ошибку, а не обещание выполнить все пропущенные слоты.

Создание run и сдвиг расписания выполняются одной транзакцией: сначала условно обновляется ещё включённая строка расписания, затем вставляется `queued` run. Если строку уже выключили или забрал другой процесс, вставки не будет. Восстановление после рестарта подбирает только `queued` schedule-runs старше нескольких секунд; уже начатый `running` run автоматически не переигрывается. Crash посреди анализа не должен выглядеть как завершённый результат и не должен незаметно запускать второй анализ.

## Владение и эксплуатационный смысл

Расписания и watch-и принадлежат workspace и подтверждённому аккаунту; API использует `require_workspace_actor`, поэтому анонимная сессия не управляет чужими фоновыми задачами. Админ-панель — это представление, а не отдельная модель владения. Пауза выключает будущие срабатывания; повторное включение делает слот готовым сразу и считает следующее время от срабатывания, а не наверстывает пропущенное. Остановка приложения идёт через async cleanup: scheduler сначала перестаёт брать новые слоты, затем ждёт свои задачи до закрытия пула БД; без PostgreSQL этот путь в текущей приёмке не исполнялся.

Для пользователя смысл такой: фоновый процесс — это durable-очередь с арендой и явными правилами переполнения, а не таймер в памяти. Для защиты: «расписание фиксирует ревизию и артефакт, сериализует один слот, не создаёт догоняющий шквал и восстанавливает только ещё не начатые queued-run».

# Уведомления и webhook: секреты, URL и честная доставка

## Настройки и секреты

Уведомления о завершении run настраиваются в workspace. GET настроек всегда возвращает пустой `webhook_url` и только `webhook_configured`, `webhook_ref` и маску вида `https://host/…`; полный URL остаётся на сервере. На PUT пустое поле означает «оставить сохранённый секрет», непустое — заменить. Ошибки валидации нормализованы: неверный тип, лишнее поле, битый JSON или слишком длинный URL дают 422 с фиксированным текстом и не отражают входные данные. Это не косметика: URL вебхука часто содержит токен в пути, поэтому его нельзя возвращать в ответе, журнале или тексте ошибки.

Пример: сохранён `https://hooks.example/team/secret-token`; GET показывает `webhook_configured: true` и маску `https://hooks.example/…`, а пустое поле сохраняет прежний секрет. Полный URL не попадает в браузер и скриншоты.

## SSRF и разрешённые получатели

Перед сохранением включённых настроек сервер проверяет структуру URL и политику получателя. Разрешены только `http/https`, без пробелов/control-символов, query, fragment и userinfo; порт должен быть корректным. Дальше работает policy: loopback разрешён только при явном `allow_local=true` и только как loopback, не как произвольная частная сеть; private, link-local, metadata и CGNAT отклоняются; внешний получатель требует `allow_external=true`, HTTPS и порт 443, а все DNS-адреса должны быть глобальными. Runtime закрепляет соединение за проверенным IP, не следует redirects, не читает тело ответа и отключает proxy из окружения. Это снижает SSRF-риск, но не делает внешний приёмник доверенным.

Пример: `http://127.0.0.1:8080/hook` можно сохранить только с `allow_local`; `http://10.0.0.5/...` не станет локальным исключением; `https://example.com:8443/...` не пройдёт внешнюю политику из-за порта.

## Семантика доставки

Outbox durable: строка создаётся при завершении run, хранит снимок URL и разрешений, а worker забирает её с lease 45 секунд. Отключение или смена URL до `authorize` переводят ещё не отправленную строку в `skipped`; после `authorize` запрос может быть уже в полёте, и код честно записывает фактический результат, а не делает вид, что отменил его. Успех — любой 2xx; 3xx не преследуется; 408/429/5xx и сетевые ошибки допускают не более трёх попыток; `retry_cancelled` навсегда запрещает повтор уже отменённого события. Гарантия — at-least-once, не exactly-once: если приёмник принял запрос, а worker умер до записи результата, возможен дубль; получатель должен дедуплицировать по `Idempotency-Key`/`eventId`. У completion-webhook нет отдельной HMAC-подписи, поэтому секретность URL — основной секрет, а стабильный id — средство дедупликации, не аутентификации. Закрепление за одним проверенным адресом означает, что при недоступном первом адресе повтор идёт туда же; это ограничение надёжности, а не расширение SSRF. Внешний TLS/приёмник в этой приёмке не проверялся.

Для пользователя: «доставлено» означает подтверждённый 2xx, «skipped» — сознательный отказ, «failed» после попыток — не обещание, что сообщение не дошло. Для защиты: «URL и секреты не покидают сервер, SSRF закрыт policy и pinning, а доставка честно at-least-once с дедупликацией на стороне получателя».

# Запуск, сборка и конфигурация

## Чистый snapshot и manifest

Сборка образа начинается не с рабочего каталога, а с проверенного коммита. `scripts/nedra-build.sh` отказывается работать, если есть изменения tracked/index, извлекает `git archive` полного HEAD во временный каталог и собирает только этот snapshot. В образ передаётся полный 40-символьный SHA: он попадает в label `org.opencontainers.image.revision` и в `release-manifest.json`. Manifest содержит revision и SHA-256 файлов runtime-состава: backend, analyzers, rag, db, docs, packages/comparison, собранный frontend/dist, а также deployment requirements и healthcheck. Dockerfile проверяет manifest после перехода на непривилегированного uid 10001; несовпадение должно остановить сборку, а не дать образу «правильный» тег с чужим содержимым.

Пример: коммит `abc…` (40 символов) даёт label `abc…` и manifest с `revision: abc…`; если в `/tmp` изменить один runtime-файл, проверка manifest обязана упасть. Для пользователя это означает, что «собрано из коммита X» проверяемо, а не является надписью на теге. Для речи точная формула такая: «образ идентифицируется полным SHA и manifest, а не плавающим тегом `latest`». В этой приёмке сам образ не собирался; проверка manifest на реальном образе остаётся шагом выкладки.

## Зависимости и runtime

`deploy/Dockerfile` — multi-stage: pinned Node image собирает frontend через `npm ci` по lock-файлу, pinned Python 3.12 image готовит wheel-кэш по `deploy/requirements.txt`, runtime ставит зависимости только из локальных wheel и копирует backend, analyzers, rag, db, docs, packages/comparison и frontend/dist. Базовые образы закреплены digest-ами, Python-пакеты — версиями; `deploy/requirements.txt` является deployment-lock и должен сверяться с `backend/requirements.txt` при изменении зависимостей. В runtime есть non-root пользователь, writable `/app/data`, tmpfs `/tmp`; для пользовательских проверок заявлен bwrap/prlimit, но фактический sandbox runtime в этой полной приёмке не запускался, поэтому нельзя обещать, что произвольный пользовательский код уже исполняется в текущем образе.

Frontend в этой сборке — отдельная ветка/commit `e46e166`; она не merged и не deployed в рамках этой задачи. Это важно: наличие `frontend/package.json` и команды `npm run build` не означает, что текущий публичный сайт обновлён.

## Конфигурация без секретов

Non-secret defaults лежат в `deploy/defaults.env`: имена образов, сеть, bind `127.0.0.1:18080`, домен, имена volume. Секреты и `DATABASE_URL` живут только в `runtime.env` с правами 600 вне git; bootstrap парсит источник без `source`/eval, проверяет канонический `KEY=value` и не печатает значения. В коде используются `DATABASE_URL`, `CG_DATA_DIR`, `CG_SESSION_SECRET`, `CG_PUBLIC_DEMO`, `CG_ALLOWED_ORIGINS`, `CG_TRUST_PROXY`, `CG_NODE_BIN`, ключ repository-webhook и настройки AI; значения в гайд не переносятся. Healthcheck строго проверяет `/api/health` и не подменяет успех авторизованным fallback.

Пример: для сборки нужен чистый SHA и заполненный `runtime.env`; если `DATABASE_URL` отсутствует, приложение должно упасть с понятной ошибкой, а не стартовать с пустой БД. Для защиты: «сборка воспроизводима по SHA и manifest, секреты не входят в git/argv, а runtime запускается от non-root».

# Готовность к эксплуатации: что доказано, что нет

## Что уже проверено

Состояние на 22 ноября 2026: проверены owning source, статическая сборка frontend в отдельной ветке, Python/Bash-синтаксис, manifest-логика, очистка lifespan на инъекциях, локальные ASGI-пробы уведомлений, asyncio-отмена и policy для literal IP. Эти проверки дают основание обсуждать архитектуру и объяснять контракты, но не являются приёмкой продукта. Полная новая сборка образа с PostgreSQL и внешними сервисами не пройдена; реальная PostgreSQL-матрица для миграций, блокировок, MVCC, lease и retry не исполнена. Поэтому нельзя говорить «всё работает» — можно говорить «код и контракты проверены в указанных границах».

Организаторские 15 — это эталонная fixture, а не результат нашего сканера; число для речи берётся из конкретного прогона. Для пользователя это означает, что обещание «готово» сопровождается перечнем пройденных проверок, а не только списком функций.

## Что требует PostgreSQL, нагрузки и restore

Для эксплуатационной готовности нужен отдельный стенд: fresh install и историческая БД, применение миграций и повторный startup, проверка notification marker/default/триггеров, гонки completion/opt-out, lease reclaim, scheduler/watch/webhook при конкуренции, а также поведение при недоступном провайдере. Нужны проверки под нагрузкой: очередь импортов, несколько watch-слотов, push-шторм, рост outbox и деградация внешнего DNS/TLS. Нужен restore-план: согласованный dump БД + app-data + globals, восстановление в изоляции и проверка, что новый образ совместим со схемой; простой rollback только тега не гарантирует данные. Отдельно нужны rootfs/uid/volume, systemd-старт и реальный публичный cutover.

Sandbox actual runtime не запускался, frontend не merged/deployed, public deployment SHA не проверен. Это не мелкие оговорки: они напрямую ограничивают обещания «можно показывать пользователю», «код исполняется изолированно» и «публичный стенд обновлён».

## Развитие и стоимость

Разумная последовательность: сначала зафиксировать exact SHA и собрать полный образ с manifest, затем прогнать PG fresh/historical и restore drill, затем проверить concurrency/нагрузку и только после этого делать frontend cutover и внешние интеграции. Стоимость растёт качественно: больше внешних провайдеров — больше секретов, квот и точек отказа; больше история и артефакты — больше БД и backup/restore; больше фоновых расписаний и push — больше нагрузки на scheduler, БД и мониторинг. Числа без замеров не называем.

Пример: если завтра обещать «push запускает проверку за секунды», сначала нужны реальная доставка провайдера, PG-конкурентный тест и restore; иначе это только архитектурное намерение. Для защиты: «готовность подтверждается exact SHA, manifest, PG/restore и нагрузочным прогоном; отсутствие любого из них — известное ограничение, а не повод для красивой метрики».
