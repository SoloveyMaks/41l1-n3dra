## Закрытый блокер: alias принимал изменённый файл

В `d33`, `backend/app/storage/migrate.py:173` и далее, mismatch выбирал alias только по имени файла и сохранённому checksum. После проверки schema marker мигратор выполнял `continue`, не связывая вычисленный checksum файла с допустимым историческим target.

Воспроизведение на собственной временной БД:

1. Применить 001/002/004/005 и finalized 006 из `3f56903`, сохранив настоящий ledger checksum `273cd694…` и guards этой версии.
2. В отдельной временной копии текущего historical 006 дописать SQL-комментарий. Это меняет checksum, не меняя schema marker.
3. Запустить `_apply_with_ledger` из точного d33 с этим файлом.

Ожидалось: отказ из-за неизвестного содержимого файла. Фактически d33 вернул `[]`, принял изменённый 006 и оставил ledger прежним. То есть контроль целостности уже применённой миграции обходился для finalized БД; сохранённая история переставала подтверждать допустимую пару содержимого и схемы.

Минимальное решение — разрешать только тройку «имя 006 + известный stored checksum + точный target checksum», дополнительно проверяя guards. Оно реализовано в `98280a0`: `backend/app/storage/migrate.py:100` задаёт target, а строка 178 отклоняет несовпадающий файл **до** проверки schema marker. В том же живом сценарии исправленный мигратор отклонил изменённый файл с причиной `exact target checksum`; ledger не изменился, 007 не зарегистрирована.

Для каждого сценария создана отдельная временная БД. Использованы настоящий psycopg, текущий `_apply_with_ledger` и SQL-файлы; подмен драйвера, unit-test файлов и изменений исходников нет. Historical/finalized схемы построены из миграций с небольшими собственными workspace/artifact/snapshot данными, это не restore production backup.

После успешной 007 **на historical и finalized путях отдельно** фактически проверено:

## Оценка 007 и границы проверки

`db/migrations/007_snapshot_origin_guards.up.sql:1` открывает транзакцию, завершаемую на строке 145. До установки guards проверяются необходимые таблицы, PK/FK и включённые исторические row guards (строки 12–73), затем hash без origin и origin без соответствующего artifact (строки 76–100). Миграция не выдумывает provenance и не переписывает данные или старые ledger rows. Deferred check добавляется на строке 119, TRUNCATE guards — на строках 132 и 137, sentinel появляется в конце той же транзакции, на строке 143.

Markers в `backend/app/storage/migrate.py:23` и SQL preflight проверяют наличие/типы/целевые relations ограничений, имена и включённость triggers; deferred guard также проверяет флаги deferrable/initially-deferred. Они **не являются полной сверкой DDL**: не сравнивают все колонки constraint, `convalidated`, определения trigger/functions. Уже записанная миграция с совпадающим checksum пропускается без повторной проверки схемы. Эти границы не следует выдавать за детектор любого ручного schema drift. В поддержанных историческом и finalized путях конкретной ошибки из-за этого не выявлено; отключённый guard перед неприменённой 007 и в alias-пути действительно отвергнут. Гипотетическая произвольная переделка схемы владельцем БД не использована как отдельный блокер.

Не выполнялись production restore/redeploy, проверка реальной production истории, UI, повторный продуктовый аудит, exhaustive перебор всех повреждений схемы и optional embeddings migrations. Утверждения владельца о production/final restore не подменяют приведённые здесь собственные результаты. Следующий шаг вне этого ревью — merge отчёта и управляемый deploy/проверка фактического production окружения владельцем.
