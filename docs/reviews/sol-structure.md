## Блокеры понимания и решения

### 1. Новый ZIP получает старый результат на том же трёхшаговом экране

**Видел в браузере:** запустил sample, получил 13 проблем / 85%. Затем загрузил `sol-structure-clean.zip`: шаг 1 уже показывает новый архив и 1 Kotlin-файл, шаг 3 продолжает показывать «Найдены проблемы», «Завершена», 13 проблем и 85%. Верхний badge тоже 13. В карточке результата нет имени проекта/времени, предупреждения о другом архиве или просьбы проверить новый.

**Что решит новичок:** новый архив уже проверен и содержит эти 13 проблем. Аналогично старый благополучный результат мог бы восприниматься как результат нового архива.

**Причина:** `App.tsx:502–525` меняет input artifact без сброса выбранного run; `UserDashboard.tsx:246–280` рисует результат отдельно без привязки к имени проекта. `handleLoadSample` имеет ещё один путь смены artifact (`App.tsx:482`).

**Минимальная правка:** единое действие смены artifact для dropdown/upload/sample; сбрасывать результат или явно оставлять его как «Предыдущая проверка проекта X» с предложением проверить новый ZIP. Во всех разделах результатов показывать выбранные проект, дату и run. Не ограничивать исправление dropdown.

### 2. «Полнота 100%» не означает полного покрытия, а причина INCONCLUSIVE скрыта от первого взгляда

**Видел в браузере:** clean run выше: первая вкладка отчёта показывает `INCONCLUSIVE`, «Полнота проверки: 100%», «Индекс полноты 100%», 1 проверенный файл, 0 пропусков/ошибок парсера и 0 находок. На первой вкладке нет причины неполного вердикта и нет предупреждений покрытия. В карте sample, напротив, явно написано «Проверено неполностью», 3 из 8 файлов, неизвестная runtime-конфигурация/guards и непроверенные binaries.

**Что решит новичок:** программа сама себе противоречит; либо 100% значит «всё проверили», либо неполный вердикт можно игнорировать. «Покрытие» scanner aggregate и покрытие карты — разные метрики, UI это не объясняет.

**Причина:** `backend/app/reports/builder.py:17–27` вычитает только parser errors и unresolved dependencies. `skippedScopes` и `expectedScopesVerified` в процент не входят. Процент назван покрытием в `UserDashboard.tsx:260` и общей полнотой в `ReportView.tsx:77`.

**Минимальная правка:** до процента показать canonical coverage status и причину неполноты по выбранному run понятными словами. Этот эвристический индекс убрать из главного результата либо переименовать с объяснением расчёта; не превращать его в доказательство полноты. Для FAIL также показывать непроверенные области: найденная проблема не делает проверку полной.

### 3. Админский «Обзор workspace» смешивает общие и выбранные данные

**Видел в браузере:** на входе «Проекты 17», «Проверки 80», «Проблемы 0», «Покрытие 100%» и clean run. После выбора более старого sample run через историю общие 17/80 остались, «Проблемы» стали 13 и «Покрытие» 85%, а «Последняя проверка» стала старой проверкой 06:14, хотя в списке уже была 06:15. Это не подсчёт всех проблем workspace.

**Источник:** `AdminPanels.tsx:39–58`: counts берутся из overview, findings/report/currentRun — из выбранного run; подпись обещает все счётчики текущего workspace. Overview DTO запрашивается лишь при изменении роли (`App.tsx:493–500`), поэтому общие числа ещё и не обновляются вместе с run history.

**Минимальная правка:** отдельно «Вся рабочая область: архивы / проверки» и «Выбранная проверка X: проблемы / покрытие». Назвать карточку выбранной, добавить дату/проект и явное обновление overview. Не выдавать количество архивов за число уникальных проектов без пояснения.

### 4. В сравнении нельзя осмысленно выбрать «до / после», автоматическая пара может сразу дать тупик

**Видел в браузере:** «Сравнить проверки» находится в шаге 3, переход и возврат работают. Селекторы перечисляют десятки UUID + `fail/inconclusive` + время, без имени проекта, сценария или снимка. По умолчанию выбраны два разных run, на «Сравнить» получено **`Comparison rejected: Baseline and current runs/snapshots must be distinct`**. Русского объяснения одинакового snapshot и следующего действия нет. Поэтому этот live проход не дошёл до успешного сравнения; узкий SQL proof здесь не проверялся.

**Источник:** `ComparisonView.tsx:49–58, 93–95, 141–144`. В список попадают succeeded и failed, заголовок же обещает опубликованные запуски; опубликованность UI не различает. Глобальная история включает расписания и другие сценарии.

**Минимальная правка:** человекочитаемые проект/сценарий/дата, короткий run ID, явное состояние публикации; выбрать пару внутри проекта и объяснить «Один снимок — выберите другую версию архива». Русские причины для невозможного сравнения. Общее `inconclusive` и SQL `pattern_disappeared` сохранять разными выводами, не обозначать последний как vetted/general fix.

### 5. Карточка проблемы объясняет «где и почему», но не ведёт к исправлению

**Видел в браузере:** открытая SECRET-URI-CREDENTIALS показывает файл/строку, риск, уверенность, snippet/trace; рекомендации, ссылки на AI-объяснение или дальнейшего шага нет. Это основной путь «нашёл проблему → что делать». В админском AI-разделе у выбранного завершённого sample есть succeeded и 13 объяснений, но из карточки туда не попасть.

**Причина:** `EvidenceCard.tsx:152` требует `finding.ai_enrichment`. `/runs/{run_id}/findings` (`backend/app/api/router.py:434`) отдаёт stored findings; `database.py:649` не присоединяет AI items из отчёта. `ai_enrichment` собирается при экспорте official JSON, а не в основном списке.

**Минимальная правка:** связать выбранный finding с AI item по ID либо добавить «Открыть рекомендацию в отчёте». При disabled/ошибке AI дать короткое предметное действие из собственного правила, например убрать/сменить раскрытый credential и перепроверить архив. Явно объяснить, что приложение рекомендует правку, а не применяет её автоматически.

### 6. Отдельный стоп-фактор: неполная маскировка sample credential

В карточке sample SECRET-URI-CREDENTIALS `src/main/resources/application.properties:6` в «Фрагменте кода» часть строки замаскирована, но пароль после второго разделителя остаётся видимым целиком. Значение намеренно не включено в отчёт; находка сразу отправлена координатору (`msg_572aa033a48c`). Это наблюдавшееся поведение готового примера, не доказательство утечки реального production credential.

Минимум до показа: исправить redaction всей строки/URI и живо проверить карточку, evidence, AI, экспорт и инспектор. Статус исправления в этот baseline review не включён.

## Что уже помогает и не требует новой архитектуры

- User после входа не видит конструктор, палитру и настройки. «Загрузить ZIP → Запустить проверку → результат» находится без инструкции; запрет запуска без архива понятен.
- Ошибка «Файл не является корректным ZIP-архивом» остаётся в диалоге и позволяет восстановиться sample без перезагрузки.
- Админские группы «Обзор / Сценарий / Результаты / Система» внятные; переходы между всеми проверенными разделами работают. Доступ не притворяется полноценной системой аккаунтов.
- «Ход проверки» отделяет выполнение от FAIL-вердикта; trigger-инспектор реально открывает вход/выход.
- Карта называет узлы «Адрес запроса / Проверка доступа / Обработчик», объясняет назначение и неизвестные связи. Это граф анализируемого приложения, а не workflow с Secret/SCA/AI blocks. Конструктор открывается отдельно.
- На карте неполнота не спрятана: неизвестные связи выделены, есть прямое «это пробел анализа, а не безопасное состояние», видны skipped scopes и отсутствие domain policy. Клик по проблеме/evidence загрузил конкретный Kotlin-фрагмент `AdminController.kt:13`, а не иллюстрацию.
- SQL-раздел исходников прямо ограничивает proof source-паттерном, не общим вердиктом и не vetted. README/handoff честно называют embeddings unavailable/optional, shared workspace и неполноту; эти ограничения надо перенести в нужные места интерфейса, а не убирать.

## Границы вывода и следующий шаг

Не проверялись в этом обходе: реальная форма отправки login, смена/истечение сессии, успешное создание/выполнение расписания, сохранение/ветвление нового workflow, уведомления, скачанный JSON/Markdown, успешная общая comparison-пара и узкий SQL before/after proof, embedding API/retrieval/vetted promotion, воспроизведение failed run с отсутствующим report, все мобильные элементы конструктора и все анализаторы. Эти проверки нельзя считать пройденными по факту существования кнопок.

Новые fix-коммиты, появившиеся в local dev во время review, не сливались поверх закреплённого baseline и не проверялись. Координатор отдельно назначает focused retest: **upload + dropdown + sample → принадлежность результата; clean run → причина неполноты вместо 100%; старый run → честный обзор; выбор пары → понятное сравнение; карточка → рекомендация; маскирование всех поверхностей.** Повторный полный редизайн для этого не нужен.
