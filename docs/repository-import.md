# Импорт проекта из репозитория и наблюдение за коммитами

Коротко: пользователь добавляет проект как ZIP или как ссылку на публичный
репозиторий GitHub/GitLab. Администратор может поставить ветку на наблюдение:
система сама проверяет новые коммиты по расписанию и запускает анализ.

## Пользователь: как проверить репозиторий

1. В редакторе проверки нажмите «ZIP или репозиторий».
2. Вкладка «Репозиторий»:
   - ссылка вида `https://github.com/owner/repo` или `https://gitlab.com/group/repo`;
   - ветка необязательна. Пустое поле — ветка по умолчанию; после импорта
     показывается фактическая ветка.
3. «Импортировать репозиторий» → проект выбран в текущем сценарии. Дальше
   собирайте блоки в редакторе и запускайте проверку.

Импорт скачивает архив репозитория и фиксирует точный коммит. Проверка всегда
относится к этому коммиту, даже если в ветке уже появились новые изменения.
Старый результат прошлого проекта очищается: новый импорт не смешивается с ним.

На карточке проекта и в результате проверки видно источник: провайдер,
`owner/repo`, ветка и короткий SHA. Источник берётся из артефакта выбранной
проверки, а не из текущего черновика. Если проверку создал сервер (например,
наблюдение за новым коммитом) уже после открытия страницы, интерфейс
подгружает артефакт этого запуска при открытии — SHA и ветка видны без
перезагрузки страницы.

### Что поддерживается

- Только публичные репозитории на `github.com` и `gitlab.com` по HTTPS.
- Приватные репозитории, токены, логины и пароли пока не поддерживаются.
  Ссылка с учётными данными отклоняется.
- Ветка — обычное имя (`main`, `release/1.0`). Пустое значение = ветка по
  умолчанию у провайдера.
- Скачивается архив исходников на выбранный коммит: без `.git`, без submodules,
  LFS-файлы могут быть заглушками. Это снимок для анализа, не рабочая копия.
- Большие репозитории ограничены общим лимитом архива: 50 МБ сжатого и
  250 МБ распакованного. При превышении импорт вернёт понятную ошибку, а не
  частичный результат.
- Повторный импорт того же репозитория после нового коммита — это новый
  артефакт с новым SHA; история старых проверок сохраняется.

### Ошибки

| Что видно | Причина |
|---|---|
| «Поддерживаются только github.com и gitlab.com» | другой хост или опечатка |
| «Приватные репозитории не поддерживаются» | 404 от провайдера или закрытый репозиторий |
| «Архив слишком большой» | превышен лимит распаковки/скачивания |
| «Провайдер временно ограничил запросы» | rate limit GitHub/GitLab |
| «Серверная часть ещё не развёрнута» | импорт/наблюдение ещё не включены на этом стенде |

## Администратор: автозапуск проверок

Админ-панель → «Автозапуск». Три явных варианта:

1. **Архив по расписанию** — прежний запуск сохранённого сценария с выбранным
   ZIP по `interval:` или cron. Работает как раньше.
2. **Проверка по таймеру** — сервер сам опрашивает ветку публичного
   GitHub/GitLab-репозитория. Указываются репозиторий, ветка (необязательно) и
   частота: `interval:300` или cron из пяти полей. Минимум 60 секунд, по
   умолчанию 300. Это опрос, а не событие: задержка до одного интервала.
3. **Пуш в репозиторий (webhook)** — GitHub/GitLab присылает событие push, и
   проверка стартует сразу после доставки. Поля частоты и cron у этого режима
   нет.

Общее для репозиторных режимов:

- При создании запоминается текущий коммит ветки. Скрытого первого анализа нет:
  сначала импортируйте проект и проверьте вручную, дальше автозапуск будет
  реагировать только на новые коммиты.
- «Пауза»/«Включить» действует на оба режима: на опрос и на приём событий.
- «Проверить ветку сейчас» — явная разовая проверка ветки, а не ожидание
  события. Возможные ответы: изменений нет, проверка запущена, уже идёт, ошибка.
- В списке видны: включено/на паузе, ошибка, последняя и следующая проверка
  (для опроса), последний коммит и ссылка на последний запуск.
- Управление доступно только роли `admin`. Пользовательская сессия этих
  запросов не делает.

### Webhook: настройка доставки

После создания доставки интерфейс выпускает адрес и секрет — один раз, по явному
действию администратора. Дальше:

- **Payload URL** — `https://<стенд>/api/repository-hooks/<id>`; в поле показан
  полный адрес, кнопка копирует его.
- **Secret** — показан в маске, кнопка копирует значение целиком. Секрет не
  пишется в localStorage/sessionStorage и в журналы; он исчезает при закрытии
  окна или смене сценария.
- **GitHub**: репозиторий → Settings → Webhooks → Add webhook; Content type
  `application/json`; Secret — скопированное значение; события — только push;
  SSL verification включён.
- **GitLab**: проект → Settings → Webhooks; URL — адрес доставки; Secret token —
  скопированное значение; только Push events.
- Хук ставится вручную и требует прав администратора репозитория. Интерфейс не
  подключает его автоматически. Бейдж «Секрет выпущен» означает готовность
  сервера, а не подтверждение установки хука.
- **Перевыпуск секрета** сразу отменяет старый: интерфейс показывает
  предупреждение и требует подтверждения, после чего хук у провайдера нужно
  обновить.
- В карточке видны последняя доставка, её статус и ошибка, последний коммит и
  ссылка на последний запуск.
- Если на сервере нет стабильного ключа для выпуска секрета, настройка честно
  отвечает «недоступна» (503), а не создаёт временные учётные данные.

API, который использует интерфейс:

```
POST  /api/artifacts/repository                    {url, branch?}
GET   /api/repository-watches
POST  /api/repository-watches                      {workflowId, url, branch?, triggerMode, cronOrInterval?}
PATCH /api/repository-watches/{id}                 {enabled}
POST  /api/repository-watches/{id}/check
POST  /api/repository-watches/{id}/webhook/setup   {rotate?:boolean}
```

Ответ setup: `{endpointPath, secret, provider, event:"push"}` с
`Cache-Control: no-store`. `endpointPath` относительный, интерфейс добавляет
`window.location.origin`.

## Ограничения и состояние

- Бэкенд-модули импорта, наблюдения и приёма пушей входят в эту ветку.
  Интерфейс проверен на изолированном PostgreSQL с реальным публичным
  GitLab-репозиторием: импорт, запуск проверки, наблюдение, моделирование смены
  коммита, запуск `repository_update` и ссылка на последний запуск. Доступность
  на публичном стенде зависит от отдельного развёртывания; при отсутствии API
  интерфейс честно показывает, что импорт/наблюдение недоступны.
- Приватного доступа, токенов и ручного выбора произвольного коммита нет.
- Событие push принимается только для настроенной ветки; теги, другие ветки и
  удалённые ветки игнорируются.
- Секреты и токены не сохраняются в браузере: ссылки с учётными данными
  отклоняются, ошибки не содержат сырых ответов провайдера.
