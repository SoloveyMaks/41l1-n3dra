# Импорт проекта из репозитория и наблюдение за коммитами

Коротко: пользователь добавляет проект как ZIP или как ссылку на публичный
репозиторий GitHub/GitLab. Администратор может поставить ветку на наблюдение:
система сама проверяет новые коммиты по расписанию и запускает анализ.

## Пользователь: как проверить репозиторий

1. «Проверка проекта» → «ZIP или репозиторий».
2. Вкладка «Репозиторий»:
   - ссылка вида `https://github.com/owner/repo` или `https://gitlab.com/group/repo`;
   - ветка необязательна. Пустое поле — ветка по умолчанию; после импорта
     показывается фактическая ветка.
3. «Импортировать репозиторий» → появляется обычный проект, дальше те же три
   шага: выбрать проект, запустить проверку, посмотреть результат.

Импорт скачивает архив репозитория и фиксирует точный коммит. Проверка всегда
относится к этому коммиту, даже если в ветке уже появились новые изменения.
Старый результат прошлого проекта очищается: новый импорт не смешивается с ним.

На карточке проекта и в результате проверки видно источник: провайдер,
`owner/repo`, ветка и короткий SHA. Источник берётся из артефакта выбранной
проверки, а не из текущего черновика. Если проверку создал сервер (например,
наблюдение за новым коммитом) уже после открытия страницы, интерфейс
подгружает артефакт этого запуска при открытии — SHA и ветка видны без
перезагрузки страницы.

### Что поддерживается

- Только публичные репозитории на `github.com` и `gitlab.com` по HTTPS.
- Приватные репозитории, токены, логины и пароли пока не поддерживаются.
  Ссылка с учётными данными отклоняется.
- Ветка — обычное имя (`main`, `release/1.0`). Пустое значение = ветка по
  умолчанию у провайдера.
- Скачивается архив исходников на выбранный коммит: без `.git`, без submodules,
  LFS-файлы могут быть заглушками. Это снимок для анализа, не рабочая копия.
- Большие репозитории ограничены общим лимитом архива: 50 МБ сжатого и
  250 МБ распакованного. При превышении импорт вернёт понятную ошибку, а не
  частичный результат.
- Повторный импорт того же репозитория после нового коммита — это новый
  артефакт с новым SHA; история старых проверок сохраняется.

### Ошибки

| Что видно | Причина |
|---|---|
| «Поддерживаются только github.com и gitlab.com» | другой хост или опечатка |
| «Приватные репозитории не поддерживаются» | 404 от провайдера или закрытый репозиторий |
| «Архив слишком большой» | превышен лимит распаковки/скачивания |
| «Провайдер временно ограничил запросы» | rate limit GitHub/GitLab |
| «Серверная часть ещё не развёрнута» | импорт/наблюдение ещё не включены на этом стенде |

## Администратор: наблюдение за новыми коммитами

Админ-панель → «Расписания» → вкладка «Новые коммиты».

- Указываются репозиторий, ветка (необязательно) и частота проверки:
  `interval:300` (секунды) или cron из пяти полей, например `*/5 * * * *`.
- Минимальный интервал — 60 секунд, по умолчанию 300.
- Это **опрос по расписанию**, а не webhook: мгновенной доставки нет, задержка
  может достигать одного интервала.
- При создании наблюдения запоминается текущий коммит ветки. Скрытого первого
  анализа нет: сначала импортируйте проект и проверьте вручную, дальше
  наблюдение будет запускать проверку только на новых коммитах.
- Кнопки: «Пауза»/«Включить» и «Проверить сейчас». Проверка сейчас возвращает
  одно из состояний: изменений нет, проверка запущена, уже идёт, ошибка.
- В списке видны: включено/на паузе, ошибка, последняя и следующая проверка,
  последний коммит и ссылка на последний запуск.
- Расписания фиксированного архива работают как раньше и не меняются.
- Управление доступно только роли `admin`. Пользовательская сессия этих
  запросов не делает.

API, который использует интерфейс:

```
POST  /api/artifacts/repository            {url, branch?}
GET   /api/repository-watches
POST  /api/repository-watches              {workflowId, url, branch?, cronOrInterval}
PATCH /api/repository-watches/{id}         {enabled}
POST  /api/repository-watches/{id}/check
```

## Ограничения и состояние

- Бэкенд-модули импорта и наблюдения входят в эту ветку. Интерфейс проверен на
  изолированном PostgreSQL с реальным публичным GitLab-репозиторием: импорт,
  запуск проверки, наблюдение, смена коммита, запуск `repository_update` и
  ссылка на последний запуск. Доступность на публичном стенде зависит от
  отдельного развёртывания; при отсутствии API интерфейс честно показывает,
  что импорт/наблюдение недоступны.
- GitHub в локальной проверке ответил ограничением частоты запросов — это
  внешнее ограничение провайдера, а интерфейс показывает читаемую ошибку.
- Webhook-режима, приватного доступа и ручного выбора произвольного коммита в
  этом шаге нет.
- Секреты и токены не сохраняются: ссылки с учётными данными отклоняются,
  ошибки не содержат сырых ответов провайдера.
