# Cyber Garden 2026 — AI Security Workflow: Полный анализ и фиксация требований

> **Документ:** Сводный разбор исходного документа `TEAM-HANDOFF.pdf` (Кейс банка «Центр-инвест», Cyber Garden 2026).  
> **Статус:** Полная проектная спецификация, фиксация архитектуры, правил, ограничений, контрактов и плана реализации для команды и агентов.

---

## 1. Общие сведения и ключевая концепция

* **Хакатон и кейс:** Cyber Garden 2026, кейс банка **«Центр-инвест»**.
* **Таймлайн:** Всего **54 часа**.
  * **H0–H8/H12:** Первый сквозной рабочий вертикальный путь (E2E).
  * **H48:** Полный Code Freeze (только багфиксы, полировка, репетиции и защита).
* **Суть продукта:** Визуальный конструктор проверок безопасности кода для небольших команд разработки. Пользователь загружает учебный Kotlin/Spring Boot-проект (ZIP-архив или ссылку на репозиторий), собирает сценарий (workflow) из блоков на канвасе, запускает вручную или по расписанию и получает детерминированный отчёт с AI-объяснением и рекомендациями:
  * Где проблема (файл, строка, колонка, контекст);
  * Почему она опасна (описание вектора атаки и последствий);
  * Насколько мы уверены в находке (`severity` vs `confidence`);
  * Как её исправить (`remediation` и патч/версия);
  * Что изменилось после повторной проверки (**Proof Loop**).
* **Философия и ключевая фраза проекта:**
  > *"Мы не просим поверить нейросети. Вот собственное правило, вот доказательство в коде, вот объяснение и вот результат после исправления."*

## 2. Обязательные требования кейса (Must Have)

1. **Визуальный drag-and-drop конструктор:**
   * Добавление готовых блоков, настройка параметров, соединение связями (рёбрами).
   * Разрешены библиотеки: `React Flow`, `Rete.js` и аналоги.
2. **Триггеры:**
   * Ручной запуск (кнопка в UI / API).
   * Запуск по расписанию (cron / interval / timezone).
3. **Логика графа:**
   * Ветвление `if/else`, операции сравнения, регулярные выражения (`regex`).
4. **Уведомления:**
   * Минимум один рабочий канал: Telegram, SMTP (Email) или HTTP Webhook.
5. **Три собственных анализатора (СТРОГО СОБСТВЕННЫХ):**
   * **Поиск секретов (Secrets Scanner):** токены, пароли, ключи, приватные ключи, URI с credentials.
   * **Анализ зависимостей (SCA):** разбор `build.gradle.kts`, `libs.versions.toml`, lock-файлов, сопоставление со справочником организаторов.
   * **Статический анализ кода (SAST):** базовый анализ Kotlin/Spring Boot приложений (Gradle Kotlin DSL).
6. **Критичность находок:**
   * Каждая находка обязана иметь уровень риска (`severity`) и явное обоснование выбора (`severityBasis`).
7. **Интеграция с LLM:**
   * Модель переводит и объясняет найденные анализаторами проблемы человеческим языком и предлагает исправления (`remediation`).
8. **Программная валидация ответа LLM:**
   * Проверка структуры ответа по JSON Schema, сверка реальных файлов и строк с детерминированными находками, запрет галлюцинаций CVE.
9. **Живое исполнение (Live Execution):**
   * Отображение состояния блоков на канвасе в реальном времени и потока данных между ними (через SSE).
10. **Рабочий прототип:**
    * Приём файлов (ZIP) или ссылки, исполнение собранного workflow, выдача отчёта.
11. **Безопасность скоупа сканирования:**
    * Сканирование только загруженного проекта и эталонных примеров.

## 3. Жёсткие запреты и ограничения

### Категорически запрещено кейсом:
* ❌ Использовать готовые сканеры: **Semgrep, Gitleaks, Trivy** и аналоги.
* ❌ Использовать **detekt** с готовыми правилами безопасности.
* ❌ Подключать любые готовые сторонние security-сканеры или чужие security rulesets.
* ❌ Отправлять исходный код в LLM и выдавать мнение нейросети за обнаружение уязвимости (LLM не ищет уязвимости, она только объясняет факты, найденные анализаторами!).
* ❌ Строить ядро платформы на готовых low-code системах: **n8n, Node-RED** и т.д.
* ❌ Проверять произвольные внешние системы.

### Архитектурное ограничение безопасности:
* ❌ **НЕ ЗАПУСКАТЬ** `gradlew`, build scripts, git hooks, annotation processors и байткод/код загруженного проекта! Анализ производится исключительно статически (чтение файлов и AST).

### Что разрешено и рекомендуется:
* ✅ Регулярные выражения (`regex`).
* ✅ Парсеры AST: `Tree-sitter` (`tree-sitter-kotlin`) или Kotlin PSI.
* ✅ Библиотеки сравнения версий (с семантикой Maven/OSV).
* ✅ Выданный организаторами JSON-справочник уязвимостей.
* ✅ `React Flow` / `Rete.js` для канваса.
* ✅ Собственный легковесный workflow-движок (DAG executor).

        ▲
        ▼

### Рекомендуемый стек:
* **Frontend:** React + TypeScript + Vite + Tailwind CSS + React Flow.
* **Backend:** Python + FastAPI + Pydantic v2 + SQLite (WAL).
* **Синтаксический разбор:** `tree-sitter==0.26.1` и `tree-sitter-kotlin==1.1.0`. Живой spike подтвердил поддержку Kotlin/KTS, CRLF, UTF-8 и диагностику синтаксических ошибок. Для интерполяций `$name` нужен собственный ограниченный post-pass.
* **События:** Server-Sent Events (SSE) с последовательным `seq` и `Last-Event-ID`.
* **LLM:** Единый интерфейс (Cloud provider / локальный vLLM/Ollama).
* **Что исключено:** Kubernetes, Kafka, Redis, Temporal, Celery, векторизация/RAG, тяжелые микросервисы.

## 6. Каталог нод графа и их контракты

### 6.1. Минимальный набор типов нод

1. `manual_trigger` — ручной запуск;
2. `schedule_trigger` — запуск по расписанию;
3. `project_input` — входной артефакт (загруженный проект);
4. `secret_scan` — собственный анализатор секретов;
5. `sca_scan` — собственный анализатор зависимостей;
6. `kotlin_sast` — собственный SAST-анализатор Kotlin/Spring;
7. `merge_findings` — слияние находок трёх сканеров в единый бандл;
8. `branch_merge` — схождение условных ветвей;
9. `condition` — ветвление логики (if/else, сравнение, regex);
10. `policy_gate` — оценка рисков по политике (pass/fail/inconclusive);
11. `ai_explain` — запрос к LLM на генерацию объяснений и фиксов;
12. `build_report` — сборка итогового структурированного отчета;
13. `notify` — отправка уведомления во внешний канал.

### 6.2. Входы и выходы нод

| Нода | Вход | Выход | Описание |
| :--- | :--- | :--- | :--- |
| **Trigger** | Ручной запрос / scheduled tick | `TriggerEvent` | Инициализация запуска с метаданными |
| **ProjectInput** | `TriggerEvent` + `artifactId` в config | `ArtifactRef` | Ссылка на проверенный локальный артефакт |
| **Любой scanner** | `ArtifactRef` | `ScanResult` | Находки (`findings`), диагностика, `coverage`, `duration` |
| **MergeFindings** | Три `ScanResult` | `FindingsBundle` | Сводный бандл с агрегированным coverage |
| **PolicyGate** | `FindingsBundle` | `PolicyResult` | Вердикт политики (`pass`/`fail`/`inconclusive`), ссылка на бандл |
| **AiExplain** | `FindingsBundle` / `PolicyResult` | `ExplainResult` | Статус, проверенные элементы `items`, модель |
| **BuildReport** | Findings, Policy, опциональный AI | `ReportRef` | Ссылка на сохраненный итоговый отчет |
| **Condition** | Выбранные безопасные поля результата | `true` / `false` + refs | Булев результат для активации конкретного control-ребра |
| **Notify** | `ReportRef` | `DeliveryResult` | Статус доставки уведомления |

> **Правило передачи данных:** На рёбрах графа передаются только легковесные `refs` и `summaries`. Большие исходники, AST и `raw credentials` наружу не передаются. Preview ребра в UI отображает только маскированный JSON.

## 7. Спецификация трёх собственных анализаторов

### 7.1. Поиск секретов (Secret Analyzer)
* **Область:** Все ограниченные текстовые файлы (`.kt`, `.kts`, `.yaml`, `.yml`, `.properties`, `.env`, `.json`, `.conf`, комментарии, документация). Бинарные и гигантские файлы маркируются `skipped`.
* **Правила поиска:**
  1. Паттерны ключей: `password`, `secret`, `token`, `apiKey`, `accessToken` со строковыми значениями;
  2. Приватные ключи (PEM-блоки `-----BEGIN PRIVATE KEY-----` и др.);
  3. URI с учетными данными: `scheme://user:password@host`;
  4. Литералы в `Authorization: Bearer ...`;
  5. Дефолтные значения в плейсхолдерах: `${ENV:default_secret}`;
  6. Ограниченная свертка `const val`, конкатенаций и интерполяций.
* **Безопасность:**
  * Папки `test` и `example` не считаются безопасными (учебные секреты часто кладут туда).
  * Сырой секрет существует **только в оперативной памяти** анализатора. До UI, логов, SSE, AI и уведомлений он заменяется маской.
  * Для группировки и дедупликации используется **HMAC**, а не обычный хеш короткого пароля.

### 7.2. Анализ зависимостей (SCA Analyzer)
* **Разбор без запуска Gradle:**
  * Чтение `build.gradle.kts`, `settings.gradle.kts`, `gradle/libs.versions.toml`, version catalogs, `gradle.lockfile`, ограниченный разбор деклараций BOM/platform.
  * Извлечение координат `group:name:version` и сверка со справочником организаторов.
* **Основания определения версии (`version provenance`):**
  * `requested_exact` — явно написана в Gradle;
  * `lock_recorded` — записана в lock-файле;
  * `graph_provided` — дана организаторами;
  * `bom_candidate` — предположена по локальному BOM;
  * `unresolved` — надежно определить нельзя.
* **Правила сравнения:**
  * Использование семантики `Maven ComparableVersion` / OSV.
  * Запрещено лексикографическое сравнение строк и применение голого SemVer / Python `packaging.version` без адаптации.
  * Неиспользованный catalog alias не считается используемой зависимостью.
  * Версия Spring Boot Gradle-плагина не равна автоматически версии всех используемых библиотек Spring.

### 7.3. Статический анализ кода (SAST Analyzer — Kotlin/Spring)
* **Технология:** `tree-sitter` строит AST, правила отслеживают передачу данных от источников к опасным операциям (sources → sinks).
* **Кандидаты правил для MVP:**
  1. **SQL Injection:** пользовательский ввод попадает в SQL-запрос;
  2. **Path Traversal:** имя файла/путь от пользователя попадает в операции чтения/записи без валидации границ пути;
  3. **Shell / Command Injection:** ввод попадает в команды ОС;
  4. **Broken Access Control:** широкий `permitAll()` на чувствительные endpoint'ы;
  5. **IDOR:** выдача объекта без проверки владельца (`Principal`/`SecurityContext`).
* **Evidence Trace:** Формирование цепочки `HTTP parameter → local variable → helper → sink`.
* **Правила оценки защиты:** `normalize()`, `@Valid` или самодельный метод `sanitize()` не считаются защитой автоматически, если в коде нет реальной санитизации. Публичные endpoint'ы `health`, `login` и stateless API могут легитимно быть `permitAll()` и без CSRF.

## 8. Единый формат находки (Finding Schema)

```json
{
  "id": "fnd_uuid",
  "fingerprint": "hash(analyzer + ruleId + normalizedContext)",
  "analyzer": "sast | sca | secret",
  "ruleId": "KOTLIN-SQL-INJECTION",
  "ruleVersion": "1.0.0",
  "severity": "critical | high | medium | low | info",
  "severityBasis": "Прямое попадание невалидированного ввода в executeQuery()",
  "confidence": "confirmed | potential | inconclusive",
  "confidenceBasis": "Полный taint-trace от @RequestParam до Statement",
  "status": "confirmed",
  "primaryLocation": {
    "path": "src/main/kotlin/com/bank/controller/UserController.kt",
    "startLine": 42,
    "endLine": 42,
    "startColumn": 12,
    "endColumn": 48,
    "byteRange": [1240, 1276]
  },
  "relatedLocations": [],
  "trace": [
    {"step": 1, "description": "Параметр @RequestParam accountId", "location": {...}},
    {"step": 2, "description": "Конкатенация в переменную sqlQuery", "location": {...}},
    {"step": 3, "description": "Вызов jdbcTemplate.query(sqlQuery)", "location": {...}}
  ],
  "redactedEvidence": "String query = \"SELECT * FROM accounts WHERE id = '\" + accountId + \"'\";",
  "advisoryIds": [],
  "coverageWarnings": []
}
```

* **Разделение понятий:** `severity` — тяжесть последствий уязвимости; `confidence` — надежность доказательства статическим анализатором.
* **Координаты:** Строки и колонки с 1; байтовые диапазоны `[start, end)`. Преобразование byte-columns в Unicode code points для UI с учётом CRLF и кириллицы.

## 9. Взаимодействие с AI и валидация

* **Контекст для AI:** Модель получает только список уже найденных проблем, замаскированные фрагменты (`redactedEvidence`) и минимальный контекст. Полный репозиторий не передается, сканеры модель не запускает!
* **Формат ответа LLM (JSON Schema):**
  ```json
  {
    "summary": "Краткая сводка...",
    "items": [
      {
        "findingId": "fnd_uuid",
        "explanation": "Объяснение уязвимости...",
        "remediation": "Конкретная инструкция по исправлению...",
        "suggestedFixedVersion": "2.7.18"
      }
    ]
  }
  ```
* **Программная проверка ответа (AI Trust Layer):**
  1. `findingId` реально существует в находках запуска;
  2. Файл и строка в UI берутся строго из исходной находки;
  3. Упомянутые CVE строго присутствуют в справочнике организаторов;
  4. Рекомендуемая версия `suggestedFixedVersion` строго присутствует в справочнике;
  5. В промпт, ответ и логи не попали `raw secrets`.
* **Fallback:** При отказе модели или нарушении формата детерминированный отчет сканеров все равно сохраняется.

## 10. Статусы запуска и вычисление вердикта

* **executionStatus:** `queued` | `running` | `succeeded` | `failed` | `interrupted` | `cancelled`.
* **securityVerdict:** `pending` | `pass` | `fail` | `inconclusive`.
* **Примеры:**
  * Анализ завершился и нашел critical: `succeeded` + `fail`;
  * Парсер не разобрал важный участок, находок нет: `succeeded` + `inconclusive`;
  * Воркер упал: `failed` + `inconclusive`;
  * Все разобрали, проблем нет: `succeeded` + `pass`.
* **Порядок вычисления вердикта:**
  1. Подтвержденная блокирующая находка дает `fail` даже при неполном покрытии;
  2. Иначе при наличии пробелов покрытия выставляется `inconclusive`;
  3. Только при полном обязательном покрытии без находок выставляется `pass`.

## 11. Killer-фичи

1. **Proof Loop («Исправил — докажи»):**
   * Сравнение двух запусков по стабильному `fingerprint`:
     * `resolved` — проблема исчезла при сопоставимом покрытии;
     * `persistent` — осталась;
     * `introduced` — появилась новая;
     * `changed` — изменилось доказательство;
     * `inconclusive` — второй анализ неполон или файл удален.
2. **Evidence Graph («Покажи путь»):**
   * Раскрытие цепочки передачи данных от HTTP-параметра до уязвимого sink (Taint-trace).
3. **AI Trust Layer («Нейросеть под присмотром»):**
   * Раздельное отображение: Факт (сканер) → Объяснение (AI) → Уверенность (доказательство) → Неполнота (coverage warnings).
   * Демонстрационный синтетический тест: отказ валидатора при подсовывании модели выдуманного CVE.
4. **Security Passport (Паспорт безопасности):**
   * Количество просмотренных файлов, сработавшие правила, ошибки парсера, неизвестные версии зависимостей, раскладка confirmed/potential/inconclusive.

## 12. Задачи со звёздочкой (после E2E)

1. **Библиотека шаблонов workflow:**
   * Шаблоны: «Полная проверка», «Только секреты», «CI/PR Gate». Клонирование со своей identity без переноса credentials.
2. **CI/CD CLI утилита:**
   * Консольный клиент, возвращающий exit code: `0` (pass), `1` (fail), `2` (inconclusive / error).
3. **Text-to-Workflow:**
   * Преобразование фразы пользователя (*«Каждый день проверяй секреты и отправляй отчёт»*) в граф нод без генерации произвольного кода.

## 14. Исполнение графа, ветвление и SSE

* **Состояния нод:** `pending` → `running` → (`retrying`) → `succeeded` / `failed` / `skipped` / `cancelled`.
* **Control-рёбра:** `pending`, `active`, `inactive`, `failed`. Блок `condition` активирует ровно один из выходов `true` или `false`.
* **Merge-ноды:**
  * `MergeFindings` ожидает результаты всех 3 сканеров; при падении одного сохраняет данные остальных и выставляет неполный coverage.
  * `BranchMerge` ждет разрешения всех входящих рёбер, объединяет активные, игнорирует `inactive`.
* **События SSE:**
  * Поля: `seq`, `runId`, `type`, `nodeId`, `payload` (замаскированный).
  * Типы: `node_status`, `finding_summary`, `coverage`, `run_status`, `delivery_status`, `resync_required`.
  * Клиент при переподключении передает `Last-Event-ID` или `after=N`.

## 15. Хранилище и безопасность артефактов

* **База данных:** SQLite в режиме WAL. Таблицы: `workflows`, `workflow_revisions`, `runs`, `node_runs`, `findings`, `diagnostics`, `run_events`, `schedules`, `schedule_occurrences`, `deliveries`, `encrypted_credentials`, `comparisons`.
* **Безопасная распаковка ZIP:**
  * Проверка путей на выход за пределы папки (`zip slip`), проверка симлинков, проверка числа записей.
  * Контроль распакованного объема (защита от zip-бомб) на лету при чтении потока.
  * Nested и encrypted архивы отклоняются.
  * Исходный ZIP хранится в закрытом хранилище по хешу с TTL, рабочая копия удаляется после завершения прогона.
* **Безопасность уведомлений:** Webhook проверяется на запрет обращений к локальным/внутренним адресам (SSRF protection). Учетные данные хранятся через `credentialRef` с шифрованием AES-GCM.

## 17. План на 54 часа и распределение команды

### График работ:
* **H0–H2:** Получение учебного проекта и эталона; выбор стека; фиксация API-контрактов; проверка LLM и уведомления.
* **H2–H8:** Первый вертикальный E2E путь: загрузка → один сканер каждого типа → отчёт → реальный AI → уведомление.
* **H8–H14:** Графический редактор, ручной и плановый запуск, `if/else`, сравнение, regex, живые статусы по SSE.
* **H14–H26:** Наращивание правил анализаторов: Tree-sitter Kotlin AST, константы, Gradle catalog, диапазоны уязвимостей, контекст SAST.
* **H26–H36:** История запусков, снапшоты, реконнект SSE, маскирование секретов, шифрование credentials.
* **H36–H44:** CI-клиент, библиотека шаблонов, Proof Loop, Evidence Graph, Security Passport.
* **H44–H48:** Прогоны на открытом проекте организаторов и безопасных мутациях; фиксы ложных срабатываний и пропусков.

3. Сократить количество сложных SAST-правил;
4. Упростить diff-экраны.
* **КАТЕГОРИЧЕСКИ НЕ РЕЖЕМ:** 3 собственных анализатора, расписание, if/else/comparison/regex, реальный вызов LLM, живые статусы, 1 канал уведомления, маскирование секретов.
